# Backup Panel

Веб-панель (админка) для централизованного резервного копирования сайтов и баз данных с множества серверов в Amazon S3 и на Windows-машины (SFTP). Работает без установки чего-либо на серверы-источники.

> Статус: **этапы 1–2 готовы** (админка, драйверы хранилищ, потоковый бэкап файлов и MySQL, запуск кнопкой «Запустить»). Не реализованы: запуск по расписанию, ретенция (удаление старых копий), уведомления, режим «архив на сервере», дашборд, скачивание. Документ фиксирует принятые решения и открытые вопросы.

## Быстрый старт (локально, Docker)

```sh
export DOCKER_BUILDKIT=0 COMPOSE_DOCKER_CLI_BUILD=0
docker compose up -d app queue scheduler db        # панель: http://localhost:8080
docker compose --profile test up -d                # тестовые S3 / «сервер» / «Windows»
docker compose run --rm app php artisan db:seed --class=DemoSeeder
```

Вход (только для разработки): `admin@backup.local` / `admin12345`. Команды для тестов и устройство движка бэкапа: раздел «Разработка» в конце документа.

---

## 1. Задача

- Есть набор серверов (15+), на каждом лежат сайты и базы данных (в основном MySQL).
- Есть целевые хранилища: **Amazon S3** и одна или несколько **Windows-машин** (через SFTP/OpenSSH Server). Одно задание может писать сразу в несколько хранилищ.
- В админке задаётся: откуда (сервер, пути, БД), куда (одно или несколько хранилищ), как часто (ежедневно / еженедельно / ежемесячно) и сколько хранить.
- Всё ведёт журнал: кто, когда, что, с каким результатом.
- Восстановление на первом этапе: **только скачивание** бэкапа.

## 2. Ключевые требования

| Требование | Решение |
|---|---|
| Ничего не ставить на источники | Только SSH (логин, адрес, порт, пароль) и штатные `tar`, `gzip`, `mysqldump` |
| Всё на одном сервере | Панель, планировщик и исполнитель — одно приложение |
| Большие объёмы данных | Потоковая передача без временных файлов, multipart в S3 |
| Стек | PHP, Laravel + Filament, всё в Docker |
| Журналирование | Запуски, построчные логи шагов, аудит действий пользователей |

## 3. Архитектура

```
┌─────────────────────────────────────────┐
│ Сервер панели                           │
│  Laravel + Filament (админка)           │
│  Scheduler (cron) → Queue (workers)     │
│  БД панели (MySQL)                      │
└───────┬─────────────────────┬───────────┘
        │ SSH (пароль)        │ драйверы хранилищ
        ▼                     ├─▶ Amazon S3 (multipart)
  Серверы-источники           └─▶ Windows-машины (SFTP)
  (tar, mysqldump)
```

### Драйверы хранилищ

Единый интерфейс: записать поток, список, удалить, скачать.

| Драйвер | Назначение |
|---|---|
| `s3` | Amazon S3 (multipart, presigned URL) |
| `sftp` | Windows-машина с включённым OpenSSH Server (Win 10/11, Server 2019+) |
| `local` | Папка на диске панели; для тестов (в WSL, например, `/mnt/c/...`) |
| `smb` | Общая папка Windows. Возможно позже, если SFTP не подойдёт |

Windows-машин может быть одна или несколько, каждая заводится как отдельное хранилище.

### Ход одного запуска

1. Проверка доступности сервера и отпечатка SSH-ключа.
2. Если нужна БД: на источнике `mysqldump … | gzip`, поток идёт в панель.
3. Файлы: `tar czf -` по каждому заданному пути, поток идёт в панель.
4. Панель пишет поток **параллельно во все выбранные хранилища** (tee): источник читается один раз. На диск панели ничего не сохраняется.
5. Проверка размера и чек-суммы в каждом хранилище, запись манифеста.
6. Применение ретенции в каждом хранилище по его собственным правилам.
7. Итог и логи — в журнал. Если одна цель упала, запуск получает статус «частично», упавшую цель можно повторить (повторное чтение источника либо копирование готового архива из соседней цели).

Медленная цель тормозит поток для остальных, поэтому для каждой цели задаётся буфер и таймаут.

### Режимы получения данных

- **Потоковый (по умолчанию):** на источнике ничего не остаётся, место на нём не нужно.
- **Архив на сервере → скачивание:** архив создаётся на источнике, затем скачивается с возможностью докачки и удаляется. Нужно свободное место на источнике. Для больших объёмов и нестабильных каналов.

## 4. Стек

- **Laravel 13** + **Filament** (админ-панель), **PHP 8.4**
- Всё в **Docker** (`docker compose`): приложение, очередь, планировщик, MySQL, S3Mock (тест S3), тестовые «серверы»
- БД панели: MySQL
- Очередь: database queue, воркер отдельным контейнером
- Расписание: `php artisan schedule:work` (в проде — cron `* * * * * php artisan schedule:run`)
- S3: `aws/aws-sdk-php` (multipart, presigned URL)
- SSH: системный `ssh` + `sshpass -e` внутри контейнера панели (пароль передаётся через переменную окружения, не в аргументах). Запасной вариант: `phpseclib`

## 5. Расписание и ретенция

Дневной, недельный и месячный бэкапы **не делаются отдельными запусками**: это умножило бы трафик и место.

- Бэкап запускается раз в сутки в заданное время.
- Бэкап воскресенья получает метку «недельный», первого числа — ещё и «месячный».
- Для каждого типа задаётся своё число хранимых копий.
- Копии, не подпадающие ни под одну политику, удаляются из хранилища.
- **Ретенция задаётся на каждую пару «задание — хранилище»:** например, в S3 хранить 7/4/6, а на Windows (там места меньше) только 7/0/0.
- Дневные копии для задания можно отключить, оставив только недельные и месячные.

Значение по умолчанию: **7 / 4 / 6** (дневных / недельных / месячных).

## 6. Базы данных

- Задаётся: хост БД, пользователь, пароль, список баз или «все».
- `mysqldump --single-transaction --routines --triggers --quick`.
- Пароль передаётся через временный файл с правами 600 или `MYSQL_PWD`, чтобы не попадать в `ps`; после выполнения удаляется.
- Фаза 2: автоопределение реквизитов из `wp-config.php`, `.env`, Bitrix `.settings.php`.
- Фаза 2: PostgreSQL (`pg_dump`).

## 7. Работа с большими объёмами

- Без временных файлов на панели: `источник → панель → хранилища` потоком.
- Размер части multipart для S3 подбирается под объём (64–128 МБ; лимит S3 — 10 000 частей на объект).
- Несколько путей в задании = несколько отдельных архивов. Упавшая часть перезапускается без повтора остальных.
- Нагрузка на источник: `nice -n 19 ionice -c3`, ограничение скорости, окно запуска, лимит параллельных запусков (по умолчанию 2).
- Длинные таймауты, повтор шагов при обрыве.
- Копии полные. Инкрементальные (`tar --listed-incremental`) возможны позже, схема данных им не мешает.

## 8. Модель данных

| Таблица | Содержимое |
|---|---|
| `servers` | имя, host, port, user, пароль (шифруется), отпечаток SSH-ключа, статус |
| `storages` | тип (`s3`/`sftp`/`local`), параметры подключения (шифруются): для S3 bucket, region, ключи, класс хранения; для SFTP host, port, user, пароль, базовая папка; префикс |
| `jobs` | сервер, пути и исключения, БД, режим, время, хуки до/после, активность |
| `job_storages` | связь задание ↔ хранилище, ретенция (d/w/m) для этой пары |
| `runs` | задание, тип (daily/weekly/monthly), общий статус (успех/частично/ошибка), начало/конец |
| `run_targets` | запуск ↔ хранилище: статус, размер, ключи/пути объектов, чек-сумма |
| `run_logs` | построчный лог шагов (ssh, dump, tar, upload, prune) |
| `users`, `audit_log` | пользователи и журнал изменений |
| `settings` | лимиты, значения по умолчанию |

Структура ключей в S3 (на Windows и в локальной папке та же структура; время — по `APP_TIMEZONE`, по умолчанию Europe/Moscow). `<job>` — неизменяемое имя папки задания (`backup_jobs.slug`), задаётся при создании из названия и не меняется при переименовании:

```
<job>/<YYYY-MM-DD_HH-MM-SS>.tar.gz                  (одна папка в задании)
<job>/<YYYY-MM-DD_HH-MM-SS>_<путь>.tar.gz            (если папок несколько)
<job>/<YYYY-MM-DD_HH-MM-SS>.sql.gz                   (дамп БД; при нескольких базах: ..._<база>.sql.gz)
<job>/<YYYY-MM-DD_HH-MM-SS>.manifest.json            (размеры, sha256, id запуска)
```

## 9. Интерфейс администратора

- **Дашборд:** последний успешный бэкап по каждому заданию, размер, статус. Красным подсвечиваются задания без бэкапа дольше заданного срока.
- **Серверы:** CRUD, кнопка «проверить SSH», определение наличия `tar`/`mysqldump`, свободное место.
- **Хранилища:** CRUD, выбор типа (S3 / Windows SFTP), кнопка «проверить подключение», свободное место на Windows-машине.
- **Задания:** форма расписания, путей, исключений, баз, ретенции; кнопка «запустить сейчас».
- **Журнал запусков:** фильтры, лог в реальном времени, повтор неудачного запуска.
- **Бэкапы:** список по заданию, скачивание: из S3 через presigned URL (трафик идёт напрямую, не через панель), с Windows-машины через панель потоком.
- **Аудит:** кто и что менял.
- Уведомления на первом этапе только в панели (подсветка и журнал). Email/Telegram — позже.

## 10. Безопасность

- Панель хранит пароли ко всем серверам, поэтому это самый ценный объект: шифрование секретов (`APP_KEY`), HTTPS, 2FA, ограничение доступа по IP/VPN.
- **`APP_KEY` нужно бэкапить отдельно**, иначе сохранённые пароли не расшифровать.
- Отпечатки SSH-ключей запоминаются при первом подключении (TOFU) для защиты от MITM.
- Windows-машина: отдельная учётная запись только на папку бэкапов, доступ к SSH только с IP панели, отпечаток ключа запоминается (TOFU).
- Бакет приватный, включено серверное шифрование (SSE). Клиентское шифрование — опционально.
- Отдельный IAM-пользователь с минимальными правами (только свой префикс). Versioning и lifecycle в бакете — защита от ошибок и шифровальщиков.
- Пароли БД на источниках не попадают в список процессов.

## 11. Риски

| Риск | Решение |
|---|---|
| Нагрузка на прод-сервер | `nice`/`ionice`, лимит параллельности, ночное окно |
| `tar`: «file changed as we read it» | Код выхода 1 считается предупреждением |
| Обрыв SSH на большом архиве | Таймауты, повтор шагов, разбиение на несколько архивов, режим «архив на сервере» |
| Не root на источнике | Предупреждение при проверке сервера о недоступных путях |
| Рост расходов на S3 | Классы хранения (IA/Glacier для месячных), исключения, инкрементальные копии |
| Windows-машина недоступна или нет места | Проверка свободного места до запуска, статус «частично», повтор цели |
| Медленная цель тормозит остальные | Буфер и таймаут на цель; при превышении цель отключается, запуск идёт «частично» |
| Длинные пути и недопустимые символы в Windows | Нормализация имён файлов архивов (только латиница, цифры, `-_.`) |

## 12. План работ

1. **Каркас (сделано).** Laravel + Filament, вход, сущности servers/storages/jobs, интерфейс драйверов хранилищ, проверки SSH и хранилищ.
2. **Ядро (сделано).** Потоковые dump и tar, запись в хранилища (сначала `local`, затем `s3` и `sftp`), журнал, «запустить сейчас». *Первый рабочий бэкап.*
3. **Расписание и ретенция.** Метки daily/weekly/monthly, ретенция по хранилищам, очистка, параллелизм, повторы, статус «частично».
4. **Наблюдаемость.** Дашборд, аудит.
5. **Скачивание и удобство.** Список бэкапов, presigned URL, режим «архив на сервере», автоопределение БД из CMS.
6. **Безопасность и развёртывание.** 2FA, ограничение доступа, supervisor/cron, инструкция установки.

## 13. Разработка и тестирование

- Разработка локально (WSL) в Docker, затем перенос на отдельный сервер тем же compose-файлом.
- Тестовое окружение: **S3Mock** (`adobe/s3mock`) вместо S3, контейнер с `sshd` + MySQL в роли «сервера-источника» и второй контейнер с `sshd` в роли «Windows-машины». Реальный Amazon S3 и реальный Windows подключаются в конце.
- Порядок проверки хранилищ: драйвер `local` (папка в WSL) → `sftp` на контейнер → реальный Windows с OpenSSH Server. Диск Windows виден из WSL как `/mnt/c/...`, поэтому `local` на такой путь тоже даёт запись на Windows.

## 14. Производительность и известные ограничения

Замеры на стенде (всё на одной машине, сеть — loopback, поэтому цифры показывают потолок кода, а не канала):

| Участок | Скорость | Вывод |
|---|---|---|
| Цикл чтения потока + sha256 | ~250 МБ/с | не узкое место |
| Запись в локальную папку | 140–200 МБ/с | не узкое место |
| SFTP (phpseclib, PHP) | 50–65 МБ/с на поток | потолок для быстрых каналов (гигабит и выше) |
| S3 (один поток, multipart) | 30–50 МБ/с на поток (S3Mock) | зависит от канала до AWS |
| gzip на источнике | ~24 МБ/с на несжимаемых данных, до ~80 МБ/с на тексте | **главное узкое место**: однопоточный gzip на чужом сервере |

Что с этим сделано: у задания есть выбор сжатия (обычное / быстрое / без сжатия — для фото, видео и готовых архивов), `pigz` используется автоматически, если установлен на источнике. Все получатели читают один поток, скорость = самый медленный из них.

Известные ограничения (не баги, но о них нужно знать):

- Если хранилище было недоступно в момент сбоя, на нём могут остаться недописанные файлы (`*.part`) и неполные наборы. Их уберёт «уборщик осиротевших файлов» вместе с ретенцией (этап 3).
- В бакете S3 нужно включить lifecycle-правило **AbortIncompleteMultipartUpload** (например, 7 дней), иначе оборванные загрузки остаются невидимыми, но платными.
- Скачивание с SFTP через панель пока буферизует файл целиком (будет переписано потоково на этапе 5).
- `tar` живого сайта не даёт согласованного снимка файлов (файл мог измениться во время чтения; это логируется как предупреждение). Дамп MySQL согласован только для InnoDB (`--single-transaction`).
- Контрольная сумма в манифесте считается по данным, пришедшим в панель, а не перечитывается из хранилища. Периодическая проверка восстановления — задача этапа 4.
- **Уведомлений о сбоях пока нет** (только подсветка в панели): до появления почты/Telegram статус нужно смотреть вручную.
- Для продакшена вместо `artisan serve` нужен nginx + php-fpm, HTTPS, 2FA, смена пароля администратора и паролей БД из `docker-compose.yml`; `APP_KEY` и БД панели нужно бэкапить отдельно.

## 15. Открытые вопросы

Решено:
- **Ретенция:** по умолчанию 7 / 4 / 6, настраивается на пару «задание — хранилище».
- **Копии:** только полные архивы. Инкрементальные возможны позже.

Открыто:
1. **Объёмы.** Размер крупнейшего сайта и свободное место на сервере панели неизвестны; по умолчанию предполагаются большие объёмы, поэтому выбран потоковый режим.

## 16. Разработка

### Запуск (всё в Docker, PHP на хосте не нужен)

```sh
export DOCKER_BUILDKIT=0 COMPOSE_DOCKER_CLI_BUILD=0   # в этой системе нет плагина buildx
docker compose up -d app queue scheduler db           # панель: http://localhost:8080  (admin@backup.local / admin12345, только для dev)
docker compose --profile test up -d                   # тестовые сервисы: s3mock, test-source (ssh root/rootpass), test-win (ssh winbackup/backuppass)
docker compose run --rm app php artisan db:seed --class=DemoSeeder   # демо-данные под тестовые контейнеры
```

Команды artisan/composer: `docker compose run --rm app php artisan ...` / `... composer ...`.

Тесты (ОБЯЗАТЕЛЬНО на SQLite в памяти, иначе RefreshDatabase сотрёт dev-БД MySQL):

```sh
docker compose run --rm -e DB_CONNECTION=sqlite -e DB_DATABASE=:memory: app php artisan test --compact
```

### Соглашения

- Наши задания называются `BackupJob` / таблица `backup_jobs`: таблица `jobs` занята очередью Laravel.
- Секреты (пароли серверов, конфиги хранилищ, пароль БД) хранятся зашифрованными через casts `encrypted`. В формах пустой секрет при редактировании = «не менять».
- Хранилища работают через `App\Services\Storage\StorageDriver` (s3, sftp, local). SSH к источникам: `App\Services\Ssh\SshExecutor` (`sshpass -e` + `ssh`, строгая проверка host key после первого подключения).
- phpseclib закреплён на ^3.0 (4.x меняет API). Образ приложения на PHP 8.4.
- Файлы в проекте создаются от имени пользователя хоста (UID 1000), не root.

### Движок бэкапа

- Запуск: `BackupLauncher::launch()` создаёт `Run` и ставит `RunBackupJob` в очередь (кнопка «Запустить» в списке заданий; ручной запуск = tier `manual`, ретенции не подлежит).
- `BackupRunner`: проверка сервера → план артефактов (tar по каждой папке, mysqldump по каждой базе) → поток `ssh 'sh -s'` (скрипт и пароль БД идут через stdin) → `StreamTee` → дочерние процессы `artisan backup:put` на каждое хранилище → проверка размера/sha256, manifest.json.
- После изменения кода движка нужно `docker compose restart queue` (воркер держит код в памяти).
- `DB_QUEUE_RETRY_AFTER` большой (12 ч), иначе долгие бэкапы перевыдаются второму воркеру.
- На одном сервере-источнике одновременно идёт один бэкап (`Cache::lock backup-server-<id>`, продлевается «пульсом»); воркеров очереди несколько (`QUEUE_WORKERS`, по умолчанию 3).
- Сторож `backup:reap` (раз в минуту в scheduler) помечает запуски без пульса > 30 мин как failed.
- `StreamTee`: буфер на получателя (`backup.tee_buffer_mb`), отключение получателя при 10 минутах без приёма данных.
- Неполный набор файлов запуска всегда удаляется (ошибка источника — со всех хранилищ, сбой хранилища — с него).
